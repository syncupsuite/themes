# ADR-003: Dark Mode via Semantic Inversion

**Status**: Accepted
**Date**: 2026-02-18

## Context

Dark mode is currently implemented by `buildSemanticTokens` in `engine.ts` with a hardcoded inversion: light's `neutral.900` becomes dark's `neutral.50`, light's `primary.500` becomes dark's `primary.400`, etc. This logic is identical for all foundations — Swiss International and Nihon Traditional get the same mechanical inversion.

The architecture review identified this as a structural gap: culturally, Nihon Traditional's dark mode might use deep indigo rather than generic neutral.900. The inversion logic being imperative and hardcoded means it cannot be customised per foundation.

Additionally, the `semantic` key in `DTCGRoot` is typed as `{ light?: DTCGTokenGroup; dark?: DTCGTokenGroup }` which hard-codes exactly two modes. High-contrast and other accessibility modes are excluded from the model.

## Decision

**Core rule**: Dark mode is implemented via semantic inversion only — never by changing primitive values. The `semantic.dark` token tree is a complete parallel of `semantic.light` with different primitive references.

**Per-foundation customisation**: Allow `FoundationData` to include an optional `darkModeMap` property that overrides specific semantic-to-primitive mappings for dark mode:

```json
{
  "darkModeMap": {
    "background.canvas": "indigo.950",
    "background.surface": "indigo.900"
  }
}
```

Unspecified paths fall back to the default inversion algorithm. This is additive — foundations that don't specify `darkModeMap` behave identically to current behaviour.

**Future modes**: The `DTCGRoot.semantic` type is extended from `{ light, dark }` to `Record<string, DTCGTokenGroup>` where the key is the mode name. Reserved keys are `light` (required), `dark` (required), `high-contrast` (optional). Custom mode keys are allowed for future extension.

## Consequences

**Positive**:
- Cultural foundations can have appropriate dark modes (Nihon Traditional gets ink-on-dark-indigo, not generic neutral)
- The two-mode CSS output (`[data-theme="dark"]` / `@media (prefers-color-scheme: dark)`) remains unchanged
- Backward compatible — existing foundations without `darkModeMap` continue working

**Negative**:
- `FoundationData` JSON Schema must be updated
- `buildSemanticTokens` becomes slightly more complex
- Foundation authors must understand which primitive path to use for dark mode overrides
