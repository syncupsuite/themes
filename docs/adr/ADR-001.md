# ADR-001: OKLCH Color Scaling

**Status**: Accepted — **blocking for themes 3-10**
**Date**: 2026-02-18

## Context

The current `packages/foundations/src/color.ts` module uses HSL-based math for color scale generation (`generateLightnessScale`, `expandSeedColor`, `hexToHsl`, `hslToHex`). HSL is not perceptually uniform — the same numeric lightness shift produces dramatically different perceived changes at different hues. This causes visible discontinuities in generated scales (e.g., `--primitive-color-schwarz-400: #999999` → `--primitive-color-schwarz-500: #121212`, a visually jarring jump).

The whitepaper specifies OKLCH as the color space for its perceptual uniformity property: equal numeric steps in OKLCH lightness produce equal perceived brightness changes across all hues.

Building 8 more cultural themes on HSL and later migrating to OKLCH means regenerating all token values — every generated CSS file, every snapshot, every visual test baseline. This decision must be made before themes 3-10 are built.

## Decision

Replace HSL-based color math in `packages/foundations/src/color.ts` with OKLCH before building any new themes.

**Implementation**:
- `hexToHsl` → `hexToOklch`
- `hslToHex` → `oklchToHex`
- `generateLightnessScale` to operate on OKLCH lightness (0–1 range) rather than HSL lightness
- CSS output: emit `oklch()` values with hex fallbacks via `@supports` for browsers that don't support OKLCH (Safari < 15.4, Chrome < 111)
- The 10-step scale (50→900) maps to OKLCH lightness: `[0.97, 0.93, 0.85, 0.75, 0.64, seed.l, 0.45, 0.35, 0.25, 0.15]`

**What does not change**:
- The `FoundationData` seed color format (still hex `#rrggbb`)
- The token tree structure
- The validation functions
- Consumer-facing API

## Consequences

**Positive**:
- Perceptually uniform scales across all cultural foundations
- Better dark mode legibility (OKLCH dark steps are more predictable)
- Eliminates the discontinuity bug visible in Schwarz/dark seed scales
- Aligns with CSS Color Level 4 standard — future-proof

**Negative**:
- Swiss International and Nihon Traditional token values will change numerically (same visual intent, different output hex values from better math)
- All downstream CSS snapshots and visual test baselines must be regenerated
- Safari < 15.4 fallback required (minor implementation cost)
- `color.ts` rewrite is non-trivial (~150 lines of math)

**Risk**: The published `@syncupsuite/themes@0.1.x` CSS values will differ from `0.2.0+` values. Document this as a breaking change in `CHANGELOG.md`.
