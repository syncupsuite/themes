# ADR-004: Tier Stacking Governance

**Status**: Accepted — implementation deferred to BrandSyncUp integration
**Date**: 2026-02-18

## Context

The current implementation has T0 protection (`PROTECTED_TOKEN_PATHS` + `validateOverride`) but no T1/T2 override stacking. BrandSyncUp is the delivery channel for tenant identity selection — when a tenant picks a design identity, BrandSyncUp must apply T1 brand overrides on top of the foundation. When a tenant customises their workspace, T2 overrides layer on top of T1.

Without a `mergeTokenTrees` function and tier metadata, BrandSyncUp cannot implement the preference model. This is the architectural pre-condition for the "Mac wallpaper" identity picker described in `DESIGN-TAXONOMY-VISION.md`.

## Decision

**Three tiers**:
- **T0** (engine defaults): The published theme. Protected tokens cannot be overridden. ← Already implemented.
- **T1** (brand overrides): Partner/operator level. Can override semantic mappings (which primitive a semantic token points to). Cannot touch primitives or protected tokens.
- **T2** (tenant fine-tuning): End-tenant level. Can override a subset of T1-permitted tokens. The allowed subset is defined per-theme in `meta.json`.

**Implementation in `@syncupsuite/tokens`**:

1. Add `TierLevel = 't0' | 't1' | 't2'` type
2. Add `mergeTokenTrees(base: DTCGRoot, override: Partial<DTCGRoot>, tier: TierLevel): DTCGRoot` function that:
   - Applies override on top of base
   - Rejects any path in `PROTECTED_TOKEN_PATHS` (T0)
   - For T1: only allows changes to `semantic.*` paths
   - For T2: only allows changes to `semantic.*` paths that are listed in `meta.allowedTenantOverrides`
3. Add `$extensions['syncupsuite.tier']` to token group types: `'t1-overridable' | 't2-overridable' | 'protected'`
4. Add `allowedTenantOverrides: string[]` to `BuiltTheme.meta`

**CSS delivery in BrandSyncUp**:
- T1 overrides injected as a `<style>` block after the theme import
- T2 overrides injected as tenant-scoped `[data-tenant="<id>"]` custom properties

## Consequences

**Positive**:
- Enables the full identity preference model in BrandSyncUp
- T0 protection remains solid — no override can touch status/focus tokens
- Clear rules for what partners and tenants can change

**Negative**:
- `mergeTokenTrees` is non-trivial to implement correctly (reference resolution order matters)
- T2 CSS injection adds a small runtime overhead per page load
- Foundation authors must annotate T2-overridable tokens in their data files
